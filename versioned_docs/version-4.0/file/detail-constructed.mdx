## Overview

A `\phpseclib3\File\ASN1\Constructed` object (hereinafter referred to as `Constructed`) most typically corresponds to either an [ASN.1 SEQUENCE](https://www.oss.com/asn1/resources/asn1-made-simple/asn1-quick-reference/sequence.html) or an [ASN.1 SET](https://www.oss.com/asn1/resources/asn1-made-simple/asn1-quick-reference/set.html) and contains one or more child elements. They're essentially [trees](https://en.wikipedia.org/wiki/Tree_(abstract_data_type)) whose leaf nodes are non-`Constructed` instances of `\phpseclib3\File\ASN1\Types\BaseType`.

The following code sample shows how to load an X.509 certificate as a `Constructed` object:

```php
use phpseclib3\File\ASN1;
use phpseclib3\File\ASN1\Maps\Certificate;

$x509 = ASN1::extractBER(file_get_contents('google.crt'));
$x509 = ASN1::decodeBER($x509);
$x509 = ASN1::map($x509, Certificate::MAP);

print_r($x509);
```
<sup>([download google.crt](pathname:///asn1/google.crt.txt))</sup>

In this example the `ASN1::extractBER()` is only needed because the X.509 certificate is a base64-encoded [PEM](https://en.wikipedia.org/wiki/Privacy-Enhanced_Mail). If it were a so-called DER (which stands for [Distinguished Encoding Rules](https://en.wikipedia.org/wiki/X.690#DER_encoding), which is a subset of the [Basic Encoding Rules](https://en.wikipedia.org/wiki/X.690#BER_encoding)) then the `ASN1::extractBER()` call would be unnecessary.

Anyway, the output of the above code snippet is this:

<SimpleX509 />

Superficially this looks identical to the [X509: Reading Certificates](x509#reading-certificates) example but there are a few key differences:

- **Helper methods not defined**

  None of the helper methods (eg. `getPublicKey()`, `listExtensions()`, `getExtension()`, `setExtension()`, etc) are present. `Constructed` classes are super generic and don't know enough about the underlying data structure to define helper methods.
- **PublicKey is a BitString**

  `$x509['tbsCertificate']['subjectPublicKeyInfo']` is _not_ an instance of `phpseclib3\Crypt\Common\PublicKey` - it's an instance of `$x509['tbsCertificate']['subjectPublicKeyInfo']['subjectPublicKey']` is an instance of `\phpseclib3\File\ASN1\Types\BitString`. This is because `Constructed` is super generic and doesn't know how to further decode that.
- **Extensions are OctetStrings**

  None of the extensions (`$x509['tbsCertificate']['extensions']`) are fleshed out. Like `$x509['tbsCertificate']['extensions'][1]['extnValue']` (id-ce-cRLDistributionPoints) is an instance of `\phpseclib3\File\ASN1\Types\OctetString`. As before, this is because `Constructed` is super generic and doesn't know how to further decode extensions.
- **getEncoded() returns empty string when changes are made**

  [getEncoded()](#getencoded) and it's subsection, [Cache Invalidation](#cache-invalidation), talk about this more, at length.
- **ASN1::TYPE_ANY types are Elements**

  This isn't a big issue in X.509 certificates (altho it may be for certain extensions) but in CMS's it's a much bigger issue from the get go. Like if a constructed TLV is encountered it can't be decoded any further without knowing what map to apply. Consequently, it'll be saved as an instance of `Constructed`.

## getEncoded()

If you wanted to get the original BER encoding of the above X.509 certificate one need simply do this:

```php
$x509->getEncoded();
```
That's not super useful, however, so let's consider how one might validate a CSR signature. CSR's are easier to deal with in this case because you don't have to look at extensions or the date or anything like that.

The easiest way to validate a CSR signature would be to call [$csr->validateSignature()](csr.mdx#validating-signatures), however, one could also do this:

```php
use phpseclib3\File\CSR;

$csr = CSR::load(file_get_contents('csr.csr'));

$result = $csr->getPublicKey()->withHash('sha1')->verify(
    $csr['certificationRequestInfo']->getEncoded(),
    substr($csr['signature'], 1)
);

echo $result ? 'valid' : 'invalid';
```
<sup>([download csr.csr](pathname:///asn1/csr.txt))</sup>

The output of that is `valid`.

In this example `CSR::load()` is being used instead of `ASN1` exclusive methods because it makes getting the public key easier and makes for a more succinct example.

In theory, for CSR's, the specific hashes could be auto set from `$csr['signatureAlgorithm']['algorithm']`, however, that doesn't work as well for (for example) X.509 certificates. Like for those, the signed cert would be the one that'd need to identify what algorithm the signing cert used - not the other way around. Plus, you should really be using `$x509->validateSignature()` instead, anyway.

`$csr['signature']` has the first byte dropped (vis-a-vis `substr()`) for this reason (from [X.690](https://en.wikipedia.org/wiki/X.690) &sect; 8.6.2.2):

> The initial octet shall encode, as an unsigned binary integer with bit 1 as the least significant bit, the number of unused bits in the final subsequent octet. The number shall be in the range zero to seven.

`substr($csr['signature'], 1)` is an over simplification of that but (1) I have never seen a DER encoded string where the initial octet was anything other than 0 and (2) even if I had I'm trying to keep this example short and sweet.

### Cache Invalidation

At this point an inquiring mind might wonder what happens to `->getEncoded()` if you change the value of something that's within the scope of the encoded variable. The answer depends on how you load it.

Revisiting our original X.509 example:

```php
use phpseclib3\File\ASN1;
use phpseclib3\File\ASN1\Maps\Certificate;

$x509 = ASN1::extractBER(file_get_contents('google.crt'));
$x509 = ASN1::decodeBER($x509);
$x509 = ASN1::map($x509, Certificate::MAP);

echo strlen($x509->getEncoded()) . "\n";
$x509['tbsCertificate']['serialNumber'] = new BigInteger('deadbeef', 16);
echo strlen($x509->getEncoded()) . "\n";
```
<sup>([download google.crt](pathname:///asn1/google.crt.txt))</sup>

In this example, the first `strlen($x509->getEncoded())` returns 805 and the second `strlen($x509->getEncoded())` returns 0. The reason being that the encoded cache has been invalidated.

Now let's switch things up:

```php
use phpseclib3\File\X509;

$x509 = X509::load(file_get_contents('google.crt'));

echo strlen($x509->getEncoded()) . "\n";
$x509['tbsCertificate']['serialNumber'] = new BigInteger('deadbeef', 16);
echo strlen($x509->getEncoded()) . "\n";
```
In this example, the first `strlen($x509->getEncoded())` returns 805 and the second `strlen($x509->getEncoded())` returns 794. This is because the X509 class recompiles the changed portions of the X.509 certificates everytime [`offsetGet()`](https://www.php.net/manual/en/arrayaccess.offsetget.php) is called.

Now let's switch things up yet again:

```php
use phpseclib3\File\X509;

$x509 = X509::load(file_get_contents('google.crt'));

$cert = &$x509['tbsCertificate'];
echo strlen($cert->getEncoded()) . "\n";                   // outputs 654
$cert['serialNumber'] = new BigInteger('deadbeef', 16);
echo strlen($cert->getEncoded()) . "\n";                   // outputs 0
echo strlen($x509['tbsCertificate']->getEncoded()) . "\n"; // outputs 643
$cert = &$x509['tbsCertificate'];
echo strlen($cert->getEncoded()) . "\n";                   // outputs 643
```
In this example the first `strlen($cert->getEncoded())` returns 654 and the second `strlen($cert->getEncoded())` returns 0. This is because it's the `X509` class doing the recompiling - not the `Constructed` class. `$x509['tbsCertificate']` is calling [`offsetGet()`](https://www.php.net/manual/en/arrayaccess.offsetget.php) on the `X509` class but `$cert` isn't an instance of `X509` - it's an instance of `Constructed`. `Constructed` doesn't know how to reencode things so it doesn't - it just deletes the cached encoding information after it's been invalidated with a change.

At this point one might wonder what the benefit of having a cache even is. [Constructed: A Case Study](file/constructed-example.mdx) shows how it can introduce gotchas. The fact that it prevents gratuitous re-encoding notwithstanding it's also needed for signature validation. Like the definition for [CRLs](/file/crl.mdx) ([RFC 5280 pp. 56](https://www.rfc-editor.org/rfc/rfc5280#page-56)) says this of the version number:

```
   TBSCertList  ::=  SEQUENCE  {
        version                 Version OPTIONAL,
                                     -- if present, MUST be v2
```

So even if we're using the distinguished encoding rules (DER) the presence of that field is still up to the discretion of the software that created the CRL and just because phpseclib encodes it one way doesn't mean that OpenSSL would encode it the same way. Like it's valid ASN.1 encoding in either case but if you reconstruct the signature subject incorrectly then a signature that would have otherwise successfully validated all of a sudden might not.

## Lazy and Eager Loading

By default `Constructed` objects are [lazy loaded](https://en.wikipedia.org/wiki/Lazy_loading). To eager load a `Constructed` object (or any class that thinly wraps around said objects) one need only do `->toArray()` on the object in question.

Some of the consequences of choosing one approach over another are discussed below.

### Speed and Memory Usage

The chief advantage of lazy loading is lower memory usage.

To illustrate this we'll use [bigcrl.bin](pathname:///asn1/bigcrl.crl), a 2.2mb CRL that has 41,326 revoked serial numbers, each with the `id-ce-cRLReasons` extension present. `120cd8` is the 40,000'th revoked serial number.

We'll use this function to do the searching:

```php
function findSN(CRL|array $crl, BigInteger $sn): ?int
{
    $list = $crl['tbsCertList']['revokedCertificates'];
    $total = count($list);
    for ($i = 0; $i < $total; $i++) {
        if ($list[$i]['userCertificate']->equals($sn)) {
            echo "found\n";
            return $i;
        }
        //unset($list[$i]->decoded);
    }
    return null;
}
```
Note the commented out `unset()`. We'll revisit that.

Now let's run `findSN()` with some eager loading:

```php
use phpseclib3\File\CRL;

$sn = new BigInteger('120cd8', 16);

$crl = CRL::load(file_get_contents('bigcrl.bin'));

// lazy load $crl
$start = microtime(true);
$crl = $crl->toArray();
$elapsed = microtime(true) - $start;
echo "eager loading took $elapsed seconds\n";

// benchmark serial number search
$start = microtime(true);
findSN($crl, $sn);
$elapsed = microtime(true) - $start;
echo "searching took $elapsed seconds\n";
echo 'peak memory usage was ' . memory_get_peak_usage() . "\n";
```
On my computer, with PHP 8.3.14, eager loading via `->toArray()` took about **2s**. Searching took about **0.01s** and peak memory usage was **~323mb**, bringing the total script execution time to about **2.01s**.

Now let's consider the same code with a suboptimal form of lazy loading. To do this all we need to do is comment out the `$crl = $crl->toArray()` line. When this is done searching, at least on my system, took **0.44s** and peak memory usage was **~151mb**. The total script execution time was **~1.57s faster**.

Superficially, one might conclude that subsequent searches would also take ~0.44s, however, that's not the case, because, unless you explictly delete the decoded results (the `unset()` I mentioned earlier), things, once decoded, remain decoded. So if you do `findSN($crl, $sn)` a second time that second time, on my system, only took **0.08s**. Not as good as the 0.01s from when we did `->toArray()` but still better than 0.44s. The peak memory usage remains _relatively_ constant.

Now let's consider a more optimized form of lazy loading wherein we do the `unset()`. ie. after we test each entry in the CRL to see if it's a match we immediately delete the decoded results. If we do that `findSN($crl, $sn)` takes **0.44s**, as before, but peak memory usage drops to **~43mb**. Subsequent `findSN($crl, $sn)` calls take **0.38s**.

So, if all you're going to be doing is looking for a single serial number, the most efficient way to do so would be to make use of the "more optimized" approach.  Indeed, this is what [`isRevoked()`, `getRevokedInfo()` and `getRevokedIndex()`](crl.mdx#isrevoked) all do.

If, however, you're going to be searching for a whole bunch of serial numbers, it'd be faster to eager load the whole CRL.

### Error Concealment

A disadvantage of lazy loading is that errors may be overlooked.

Consider the following lazy loaded X.509 certificate:

```php
use phpseclib3\File\X509;

$x509 = file_get_contents('google.crt');
$x509 = ASN1::extractBER($x509);
$x509[100] = '.';
$x509 = X509::load($x509);
print_r($x509['tbsCertificate']['extensions'][1]->toArray());
```
<sup>([download google.crt](pathname:///asn1/google.crt.txt))</sup>

The `id-ce-cRLDistributionPoints` extension is able to be displayed without issue.

Now consider the following eagerly loaded X.509 certificate:

```php
use phpseclib3\File\X509;

$x509 = file_get_contents('google.crt');
$x509 = ASN1::extractBER($x509);
$x509[100] = '.';
print_r(X509::load($x509)->toArray());
```
That throws an Exception.

Lazy loading only results in exceptions being thrown if you try to access the malformed part of the X.509 certificate. So like `$x509['tbsCertificate']['extensions'][1]->toArray()` doesn't result in an error but `$x509['tbsCertificate']->toArray()` does.

But where exactly is the error? That brings us to our next topic of discussion.

### Security Implications

phpseclib v1 - v3 utilize a two-step parsing process for ASN.1 structures. First, they **fully decode** the entire ASN.1 blob into a nested PHP array. Only after the entire structure is in memory does it attempt to map that data to a specific schema (such as an X.509 Certificate, CRL, or CMS).

This creates a potential denial-of-service vector. An attacker can craft a technically "valid" ASN.1 blob that is packed with high-complexity elements - like many large Object Identifiers (OIDs) - but is ultimately invalid as a certificate.

#### Example Attack Payload
```php
use phpseclib3\File\ASN1;
use phpseclib3\Math\BigInteger;

$map = [
    'type' => ASN1::TYPE_SEQUENCE,
    'min' => 1,
    'max' => -1,
    'children' => ['type' => ASN1::TYPE_OBJECT_IDENTIFIER]
];

$raw = [];
for ($i = 0; $i < 50; $i++) {
    // floor(3583 * 8 / 7) + 2 == 4096
    $oid = '2.25.' . BigInteger::random(3583 << 3);
    $raw[] = $oid;
}

$encoded = ASN1::encodeDER($raw, $map);
```
Prior to the security patches in **3.0.52, 2.0.54, and 1.0.29**, attempting to load this payload via `$x509->loadX509($encoded)` could hang the CPU for **30 seconds or more**. Even though the structure isn't a valid certificate, the "eager" parser decodes every malicious OID before the mapping phase fails.

The fix, for those versions of phpseclib, was to reduce the maximum allowed size for a single OID from 4096 bytes to **128 bytes**, which is more than sufficient for any legitimate OID while preventing the bitwise shifting overhead from becoming a DoS vector.

In contrast, **phpseclib v4** is immune to this class of issue by design because it decodes **on demand**.

When you call `X509::load($encoded)`, the library does not decode the interior elements immediately. Instead, it creates a "map" of the structure's offsets. An OID is only decoded if the application explicitly attempts to access that specific field (e.g., fetching the signature algorithm).

With the above example payload, which does not match the structural template of an X509 certificate, an exception is thrown **instantly** before it ever reaches the OID decoding logic. This "fail-fast" behavior provides a massive security boost, as malicious interior data is never even processed.

:::caution Why OID parsing is expensive
In an OID like `1.2.840.10045.3.1.7`, each number is called an **arc**.

Unlike a fixed-width integer, arc length is arbitrary. Using a [Variable Length Quantity (Base 128)](https://en.wikipedia.org/wiki/Variable-length_quantity) encoding, the parser must inspect the 8th bit of every byte:
* If it's **1**, the arc continues to the next byte.
* If it's **0**, the arc ends.

To calculate the final value, the parser must strip those 8th bits and "stitch" the remaining 7-bit chunks together. For massive, attacker-crafted OIDs, this requires intensive bit-shifting and BigInteger math. While most common arcs are small, the parser must be prepared for much larger values, like [128-bit UUIDs encoded under the 2.25 arc](https://healthcaresecprivacy.blogspot.com/2011/02/creating-and-using-unique-id-uuid-oid.html). Because these values exceed the 64-bit limit of native PHP integers, phpseclib uses BigInteger to ensure standards compliance and prevent overflow errors.
:::

#### Comparison Summary

| Feature | phpseclib v1 - v3 | phpseclib v4 |
| :--- | :--- | :--- |
| **Parsing Model** | Eager (Full Decode first) | Lazy (Decode on-demand) |
| **Memory Profile** | Spikes with input size | Constant (Stream-based) |
| **Vulnerability Fix** | Hard-coded size limits | Architectural isolation |
| **Performance** | Blocked by complex children | Instant failure on invalid maps |

## Error Pinpointing

Consider the following code:

```php
use phpseclib3\File\X509;

ASN1::enableBlobsOnBadDecodes();

$x509 = file_get_contents('google.crt');
$x509 = ASN1::extractBER($x509);
$x509[100] = '.';
$x509 = X509::load($x509)->toArray();
print_r($x509);
```

## Array-Like Interface

Despite being an object, the dynamic elements of `Constructed` objects are accessed using array syntax. eg. `$x509['tbsCertificate']['extensions']`. This is due to `Constucted` objects implementing the [`ArrayAccess`](https://www.php.net/manual/en/class.arrayaccess.php) interface.

Because `Constructed` objects implement the [`Countable`](https://www.php.net/manual/en/class.countable.php) interface you can do `count($x509['tbsCertificate']['extensions'])` and because `Constructed` objects implement the [`Iterator`](https://www.php.net/manual/en/class.iterator.php) interface you can do `foreach` on a `Constructed` object.

There are some things that PHP can do with arrays that don't make a lot of sense in the context `Constructed`. For example, it's unclear why one would want to [`sort()`](https://www.php.net/sort) a `Constructed` object. It is actually for that reason that `Constructed` objects do NOT implement the [`ArrayObject`](https://www.php.net/manual/en/class.arrayobject.php).

That said, there are other things that PHP can do with arrays that _would_ make sense for `Constructed` objects to support but for which no mechanism exists in PHP. The most notable example of this is probably [`array_keys()`](https://www.php.net/array-keys), however, one can get similar functionality by doing `->keys()`.
